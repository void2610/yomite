# ワークフロールール — 講演「認知負荷の減らし方」から Yomite 運用へ

スライドのうち、サイト機能ではなく Muse 側の運用に属するものを、再現可能な形で残す。
出典スライド番号は `slide-inventory.md` に対応する。

## 報告の出し方（15, 66）
- 結論が3行を超える報告、または表を1つでも使う報告は、HTML 1枚にして Yomite へ publish する。チャットには結論とリンクだけを書く。
- 私（人間）に判断してほしい点は、末尾にまとめず該当箇所に置く（29）。
- 修正を見せるときは、左に修正前・右に修正後を並べる（35）。変えた1文だけではなく、節の話題と前後の段落も載せる（36）。
- 推奨は1つに決めて反映したものを見せる。代替案は迷ったときだけ、最大2つまで（37）。

## 書かないルール（38, 39）
- 説明欄に経緯・言い訳・却下された案を書かない。
- 同じ一覧を何度も読ませない。

## 判断ページの作法（27〜33）
- 点検は観点別チェックリストに分けて順に行い（表記ゆれ／事実の裏取り／リンク切れ／図の位置）、判断が要るものだけを人へ出す（27）。
- 判断点は赤枠で目立たせ、「判断n／全N」を数える（28, 29）。
- 返事をしなければ OK の合図。コメントを付けた項目だけ直し、付けなかった項目はそのまま反映する（30）。
- 回答の回収は「選んだ結果をまとめてコピー」→ 1行ずつ「質問 選択肢（コメント）」を貼る形。貼られたら反映から書き出しまで一気に進める（32, 33）。部品は `public/review.js` / `public/review.css`（`/kit/` で配信）。

## 公開前チェック（64）
- HTML を出す前に `scripts/lint.mjs` を通す。publish 時は `scripts/publish.mjs` が自動で警告を出す（警告のみ、公開は止めない）。
- チェック: 図が1枚も無いページ／AIっぽい言い回し／表の見出しと色の崩れ。
- スクリプトが通ったあと、仕上がりの見た目だけ人間が確かめる。

## インボックスと巡回（20〜22）
- スマホからは Yomite のインボックスに本文1つで置く。案件名は任意、画像も付けられる。
- Mac 側の取り込みは `scripts/inbox-fetch.mjs`（原典の `/inbox` 相当）。
  - ※Yomite では Izumi様の指示により、投稿の瞬間に yomite@muse.ai へ通知メールも送る（原典は「通知は付けていない」プル型。この差分は意図的）。
- 「巡回して」と言われたら: 溜まった連絡を集め直し、返事が要る件は1件ずつ別のセッションで並行に進める。どれも送信の直前で止まり、人間の「送って」を待つ（22）。

## セッション名の状態絵文字（23）
- スレッド名係が10分おきに、セッション名の頭へ状態絵文字を付ける: ⏳ 作業中／✅ 終わった／⚠ 私の番。
- 人間が見るのは ⚠ が付いたものだけ。
- 最小実装: `scripts/session-status.mjs`（状態→絵文字の決定と付け替え。`--watch` で10分間隔）。

## 音声から企画案ページ（24）
- 思いつきを数分しゃべると、番号付き節・要旨・対比フロー図を持つ企画案ページにまとめて Yomite へ出す。書式は `templates/report.html` と `/kit/report.css`。

## 学習と検査（41〜43）
- 「学習しといて」と言われたら、その場の対処・好み・決まったやり方を設定（メモリ／運用ファイル）に書き足す。設定が増えてきたら大掃除もする（42）。
- 同じ指摘が2回来たら、注意書きではなく検査にする（lint や hook のような、忘れても止まる仕組みへ昇格させる）（43）。
- つまずきの診断は /insights 相当の振り返りで行い、「やり方の取り違え」を優先して潰す（41）。

## 開発での確認（50, 57〜59, 61〜63）
- レビューの重心は前（技術選定を決め切る）と後（動くかを確かめる）。途中のコードは読まない（50, 57）。
- 動作確認は質問集にして渡す: `templates/e2e-cases.json` の形式（質問 `q` と期待ツール `tools`）で本番に流し、回答を自動判定する（58）。
- 確かめ方そのものも設定ファイルに書いておく（59）。
- 「直りました」は本当か: 検査1＝本番の設定を読む、検査2＝使う人の手順で通す。この2つが通るまで「完了」と言わない（63）。
- ブラウザで試させる検証: 想定外の値を入れて、画面で弾かれるまで繰り返す（62）。
- モデルの乗り換え検討は、一晩試させて朝に結果を読む（同じ依頼→両方に作らせる→並べて比べる→プロンプトを直す、の反復）（61）。
